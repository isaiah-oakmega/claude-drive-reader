# 07 非功能需求與建議項目

原文第 6 節「建議但非強制」，但多數與驗收重點（順暢、安全、穩定、README 可用）直接相關，實務上應視為必做。

## NFR-1 錯誤處理 [建議]

訊息是否**清楚**，至少涵蓋：

- **授權失敗**：例如使用者拒絕授權、callback 失敗、token 交換失敗、token 過期或被撤銷。
- **檔案無法解析**：例如 PDF 無法抽取文字、圖片無法抽取文字、不支援的檔案類型。

（推論）其他應有清楚訊息的情境：

- 尚未授權就請求讀取 → 引導使用者完成授權。
- 無權限存取該資料夾／檔案（例如帳號未接受分享邀請）。
- 找不到檔案或資料夾 ID 錯誤。
- 後端無法連線、Google API 錯誤或限流。
- 檔案過大。

訊息對象包含 Claude（需能據此給使用者正確建議）與終端使用者。

## NFR-2 Token 保存 [建議]

- 保存方式需**合理**。
- **不需要過度設計**。
- **但別明碼寫死**（不可把 token、client secret 等硬寫在程式碼或 commit 進 repo）。
- 保存方式需在 README 與架構說明中交代（見 [05](05-deliverables.md)）。

## NFR-3 README 可用性 [建議／實質必要]

- README 是否讓一個**沒看過你程式碼的人**也能照著裝起來。
- 此項同時出現在第 3 節驗收方式（以粗體強調），實質為必要。

## NFR-4 安全性 [必要，來自驗收重點]

- OAuth 流程需「**安全**」。
- 最小權限：測試資料夾只給檢視權限，應只要求唯讀 scope。
- 細節建議見 [08 實作考量](08-implementation-notes.md#安全性)。

## NFR-5 穩定性 [必要，來自驗收重點]

- 讀取路徑需「**穩定**」。
- 驗收者環境不同於開發環境，需避免依賴本機特定路徑、特定 OS、未宣告的全域依賴。
